## 2. Supported Event Types & Business Handling

| Razorpay Event Type | Internal Handler Action | State Machine Transition |
| :--- | :--- | :--- |
| **`order.paid`** | Primary payment settlement event. Idempotently verifies order and confirms customer appointment. | `Payment: SUCCESS`, `Appointment: CONFIRMED` |
| **`payment.authorized`** | Fallback capture event. Invokes `captureRazorpayPayment` REST API and transitions reservation to confirmed. | `Payment: SUCCESS (Auto-Captured)`, `Appointment: CONFIRMED` |
| **`payment.captured`** | Confirms fund capture. Idempotently updates payment ledger and triggers confirmation SMS/email receipt. | `Payment: SUCCESS`, `Receipt: GENERATED` |
| **`payment.failed`** | Logs customer failure reason (card decline, UPI timeout, etc.). **Guarded against out-of-order regression.** | `Payment: FAILED (unless already SUCCESS)` |
| **`refund.processed`** | Updates ledger with refund ID, logs audit trail for salon accounting. | `Payment: REFUNDED` |

## 3. Cryptographic Signature Verification & Timing-Safe Comparison

In `src/app/api/webhooks/razorpay/route.ts` and `src/lib/payments/razorpay.ts`:
```typescript
const expectedSignature = crypto
  .createHmac("sha256", webhookSecret)
  .update(rawBody)
  .digest("hex");

const signatureBuffer = Buffer.from(receivedSignature, "utf8");
const expectedBuffer = Buffer.from(expectedSignature, "utf8");

if (
  signatureBuffer.length !== expectedBuffer.length ||
  !crypto.timingSafeEqual(signatureBuffer, expectedBuffer)
) {
  return NextResponse.json({ error: "Invalid signature" }, { status: 400 });
}
```
- **Timing-Attack Resistance:** `crypto.timingSafeEqual` prevents side-channel timing analysis attacks by guaranteeing constant-time comparison regardless of how many bytes match.

## 4. Event ID Retrieval & Deduplication Architecture

1. **Header Identification:**
   The application authoritatively reads the unique event identifier:
   ```typescript
   const eventId = req.headers.get("x-razorpay-event-id") || event.id || `${event.event}_${Date.now()}`;
   ```
2. **Database Idempotency Check:**
   Before processing any state changes, the repository checks Neon PostgreSQL:
   ```typescript
   const existingEvent = await prisma.webhookEvent.findUnique({
     where: { eventId }
   });
   if (existingEvent) {
     return NextResponse.json({ status: "already_processed", eventId }, { status: 200 });
   }
   ```
   Duplicate webhook deliveries (Razorpay retries on temporary network timeouts) return HTTP 200 immediately without double-crediting payments or generating duplicate receipts.

## 5. Out-of-Order Regression Protection

A critical production edge case occurs when webhooks arrive out of sequence (e.g. `order.paid` arrives first and confirms the appointment, followed seconds later by a delayed `payment.failed` event from a previous abandoned attempt on the same booking).

### Source Code Protection in `src/lib/db/repo.ts:verifyRazorpayPayment`:
```typescript
// Guard against regression: Never overwrite a previously successful transaction
if (existingTx && existingTx.status === PaymentTransactionStatus.SUCCESS) {
  if (!signatureValid) {
    logger.warn(`[PAYMENT_IDEMPOTENCY_GUARD] Received failed signature for already successful transaction ${orderId}. Ignoring failure.`);
    return {
      success: true,
      appointment: existingApt,
      paymentRecord: existingRecord,
      idempotent: true
    };
  }
}
```
**Outcome:** A confirmed booking and settled payment can NEVER be cancelled or marked as failed by out-of-sequence webhook retries.
